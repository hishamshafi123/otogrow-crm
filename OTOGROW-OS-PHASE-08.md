### 2026-11-05 — content posting workflow implementation decision (IMP-30/34/37/39/40)

**Outcome and complete workflow:** responsible staff must see what each brand intends to post, on which account/channel, by whom, when, and what is waiting for independent approval. Add a normalized content planning workspace with scoped account metadata and per-platform posting packages: idea/context → chosen approved native creative or text-only work where appropriate → exact caption/account/format/planned-time package → independent posting review → explicit manual publication evidence. Preserve existing manual CONTENT records through a labelled legacy entry; never silently reinterpret their old approvals or dates. No connected publishing, scheduler or growth-metric ingestion is implied. These require provider adapters and separate real-account acceptance.

**Alternatives and decision:** existing CONTENT already has separate posting review, while native delivery submissions freeze creative output/description rather than the later social account, caption and publication time. Reusing native asset approval alone would falsely authorize a different posting package. Extending every native submit/review/reopen/fulfilment path would couple social publishing to service delivery. Keep creative production and approval in the existing native task; reuse its exact approved submission/assets, then clearly label the distinct “Approve this post” decision. Do not create another production task board or auto-create work for each record. Native task fulfilment remains unchanged.

**Data and cross-system constraints:** public account metadata is separate from credentials/provider connectivity, bound to its current project/client. Each platform variant owns an immutable reviewed package and its own publication outcome; an Instagram result cannot mark Facebook published. Edits to unpublished copy/account/time/format/assets require a fresh version and review. Published packages/evidence remain historical and immutable. Current project/client/member/role and exact native task/asset visibility must apply before lists, counts, detail, preview, review or evidence writes. Reuse source-owned request receipts, bounded reads, append-only activity and normalized concurrency/retention patterns. No legacy Operations JSON rewrite, paid model/provider call or real social post is needed for local engineering.

**UI/UX:** use one compact list/calendar with visible planned date/timezone, account/channel, owner, stage and next action; maintain separate current and historical package details and clear per-platform counts. Progressively disclose account setup and history, provide actionable missing owner/reviewer/asset requirements, and preserve exact drafts through navigation/outages while clearing them on confirmed access loss. Planned dates are labelled planned until an actual provider schedule exists. Recording a public URL is a team attestation of manual publication, not verified provider success. Reuse existing scope/setup/review/receipt patterns and inspect keyboard, desktop and320/390px journeys.

**Acceptance before completion:** actual PostgreSQL schema/permission/version/native-asset/stale-source and independent-session request tests; original-preserving migration and fixture cleanup; complete plan→variant edit→independent posting review→partial manual publication→immutable history journey, including no self-approval, no double publication/receipt, failed/uncertain manual evidence honesty, draft/outage/revocation and responsive focus. Functional and design limits remain visible. This starts IMP-30 implementation without a new user approval gate; live publishing/growth stays unfinished.

Business refinement during implementation: a project’s native Company link is not proof that it has a paid client contract; Otogrow’s own content can also link its Company record. Engagement/service context therefore remains optional for every project. If selected, the pair must belong to the exact current project/company and a currently listed service; removing that source blocks further posting actions until corrected. Unlinked posts never imply service fulfilment. Requiring an engagement merely because companyId exists was rejected because it would force a fictitious client retainer for internal brand work. Calendar labels describe posts by their planned date, including any selected published/cancelled states, and never imply an external platform schedule.

Review refinements before acceptance: expose the latest manual failed/uncertain attempt for the current package in both the list and detail, because an Approved status alone hides unresolved publication. A new version does not inherit the previous version’s attempt. Native creative links open the exact approved submission in the current creative workspace. Resource-specific native visibility fingerprints must not be compared to the account-choice fingerprint; each resource revalidates its own actor/project/source access. TikTok manual packages support a single image as well as video, consistent with the current [official photo-post documentation](https://developers.tiktok.com/docs/en/content-posting-api-reference-photo-post); this does not add an API connection or multi-image carousel support.
